# Dependency Watch starter kit

Everything you need to build **Dependency Watch**. Read the problem statement first.

## Start the kit

From this folder:

- **Docker:** `docker compose up --build`
- **Podman:** `podman compose up --build` (needs `podman compose` or `podman-compose`)

This starts:

| What | Address | Purpose |
| --- | --- | --- |
| Vulnerability feed | http://localhost:7100 | A mock feed of security advisories in OSV format (https://ossf.github.io/osv-schema/). The advisory IDs are made up for this kit. |
| Webhook receiver | http://localhost:9900 | Stands in for chat and email. Anything POSTed to it appears on its page. `GET /api/received` returns the list as JSON; `DELETE /api/received` clears it. |

If a port is already in use, choose another: `FEED_PORT=7150 WEBHOOK_PORT=9950 docker compose up --build`.

## The vulnerability feed

| Request | Returns |
| --- | --- |
| `GET /v1/advisories` | Every advisory in the current feed |
| `GET /v1/advisories?ecosystem=npm` or `?ecosystem=PyPI` | One ecosystem only |
| `GET /v1/advisories?modified_since=2026-11-10T00:00:00Z` | Only advisories changed after that time |
| `GET /v1/advisories/DW-2026-0001` | One advisory |
| `GET /control/state` | Which feed is being served |
| `POST /control/feed/2` | Switch to the updated feed |
| `POST /control/feed/1` | Switch back to the original feed |

Real feeds change over time. The updated feed adds, changes and withdraws advisories, so you can see what Dependency Watch does when that happens. For example: `curl -X POST localhost:7100/control/feed/2`.

## The services: `services/`

Eight Acko services. Each folder has a `service.yaml` describing the service (its owner, its tier from 1 = most critical to 3, and whether it's reachable from the internet) and its dependency files:

| Service | Ecosystem | Files |
| --- | --- | --- |
| `payments-svc`, `quote-svc`, `notifications-svc`, `renewals-svc` | npm | `package.json`, `package-lock.json` |
| `claims-svc`, `policy-svc`, `kyc-svc`, `docs-gen-svc` | Python | `requirements.txt`, and where present `requirements.lock` and `requirements-dev.txt` |

- `package-lock.json` files use lockfile version 3.
- `requirements.lock` files are generated by pip-compile: every package is pinned, with `# via` comments showing what pulled it in.

## Changing services' dependencies

`scripts/change.sh` simulates teams upgrading packages, so you can see how Dependency Watch reacts:

```
bash scripts/change.sh list                  # show the available changes
bash scripts/change.sh fix-quote-axios       # quote-svc upgrades axios and follow-redirects
bash scripts/change.sh revert-quote-axios    # quote-svc goes back to the old versions
bash scripts/change.sh fix-payments-jwt      # payments-svc upgrades jsonwebtoken to a new major version
bash scripts/change.sh revert-payments-jwt   # payments-svc goes back to the old version
bash scripts/change.sh reset                 # put every service back as shipped
```

## Rules

- **Don't edit the files in `services/` by hand, or change the feed server.** Use `scripts/change.sh` to change dependencies. The evaluators test your product against the original kit.
- How Dependency Watch reads the services' files (from this folder, through an upload, or both) is your decision.
