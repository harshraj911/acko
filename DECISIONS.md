# Decisions

- Dependency Watch code stays outside `dependency-watch-starter-kit/`; scanning reads kit manifests and never edits or runs the kit's change script.
- When a dependency-change scenario is needed for testing, invoke the supplied `scripts/change.sh` from Git Bash at its existing kit path. Never manually alter kit dependency files as a workaround, and restore the shipped state with the script after a scenario.
- The kit root is configurable with `KIT_PATH`. Feed and webhook URLs use `FEED_URL` and `WEBHOOK_URL`, defaulting locally to `http://127.0.0.1:7100` and `http://127.0.0.1:9900`. Compose overrides them with service DNS names. SQLite location uses `DATABASE_URL`.
- Python package comparison keys use PEP 503 normalization (lowercase and collapse runs of `.`, `_`, and `-` to `-`). Original names remain available for display.
- Development-only packages are included in scan snapshots and findings, marked `dev_only`, and receive lower deterministic priority than runtime findings.
- npm package instances are keyed by lockfile install path; identical names at different nested `node_modules` paths remain distinct instances.
- Python's `requirements.lock` pins supply resolved versions. Pip-compile `# via` comments are used to derive parent relationships. `requirements-dev.txt` packages are scanned separately and tagged dev-only.
- **Unresolved manifests:** `docs-gen-svc` has no `requirements.lock`. Its `requirements.txt` constraints are stored as declared specifiers with `version = null` and `resolved = false`; no version is guessed and no vulnerability finding is asserted. Matching advisory candidates are recorded as unverified observations.
- Each scan session owns immutable `scan_results` and `dependency_relationships`; later scans append snapshots rather than updating older rows. Findings point at first and latest observations, while observations retain per-scan match state.
- Advisory IDs are upserted. Each changed raw payload is retained in `advisory_revisions`; affected ranges are refreshed from the current advisory. Withdrawn advisories remain stored and their findings are marked resolved with reason `withdrawn`.
- Source severity text is preserved. `MODERATE` is displayed as `Medium`, but source severity is not rewritten and calculated priority is not represented as CVSS.
- Risk weights are centralized in `RISK_WEIGHTS` in `backend/app/services/risk_engine/scoring.py`: severity LOW/MODERATE/HIGH/CRITICAL = 1/3/5/8; service tiers 1/2/3 = 3/2/0; internet-facing = +2; no feed-published fix = +1 (a known fix = 0); patch/minor/major/unknown complexity = 0/1/2/1; dev-only = -2. Scores clamp at zero. Priority bands are Low 0-2, Medium 3-6, High 7-9, Critical 10+. These are deterministic product heuristic points only, never CVSS.
- **Scoring cap:** after raw weighted score is calculated, priority is capped at one band above the feed severity band: LOW -> at most Medium, MODERATE -> at most High, HIGH -> at most Critical, CRITICAL -> Critical. If applied, the breakdown adds an `Advisory severity cap` factor with the score adjustment and explanation. This prevents environmental context from inflating a low-severity source advisory without limit.
- Risk breakdown reports each source and contribution. Feed severity remains in its original vocabulary; `MODERATE` maps to `Medium` in display only. Critical notifications are sent only when the computed heuristic priority is Critical; the webhook severity field retains the original feed label.
- Recommendation complexity is derived from the installed-to-fixed release components: patch, minor, or major; if no exact fixed version applies, no version or complexity is fabricated. A fixed version is selected only from the affected range containing the installed version. Known npm lockfile parent paths are used to identify the direct parent to update; missing graph evidence is stated explicitly.
- Default finding due dates are 1 day for Critical, 7 days for High, 30 days for Medium, and 90 days for Low, measured from finding creation. Owners default to the owning team in `service.yaml`.
- Findings remain Open, In Progress, or Resolved. A user-requested resolution triggers a fresh service scan and returns conflict while the vulnerable instance is still present. Automatic resolution also records the verifying scan. Finding events retain before/after data and reappearance reopens the prior finding rather than creating a duplicate.
- Scan-to-scan changes are attached to the new scan as package added/removed, version changed, scope changed, relationship added/removed, and vulnerability new/resolved/reappeared records. Timeline API returns them in creation order.
- Webhook JSON shape is `{event_type, service, package, advisory_id, severity, priority, finding_id, reference}`. Delivery rows are unique by event/finding key, store attempts and receiver responses, and regard success only when HTTP is successful and JSON contains `ok: true`. The check endpoint compares the stored payload with the receiver's `GET /api/received` response. Failed POSTs are retained and do not abort scans.
- Analytics aggregate stored findings, finding events, scan sessions, and service metadata only. Package totals use the latest completed scan per service to avoid summing repeated snapshots. Time series are daily cumulative counts from `finding_events`, include only observed event-days (short history stays short), and expose dev-only filters rather than hiding development findings.
- Scans are background jobs. Progress records file events from the scanner parser and per-package matching work; persisted polling state is authoritative, while SSE is an in-process live stream. Batch progress tracks completed services across the selected services.
- The periodic overdue worker checks every `OVERDUE_CHECK_SECONDS` (default 30); one unique delivery key per finding prevents repeated notifications. A fresh database imports services and the feed then queues a real initial scan; initialization is not run on databases already containing scan sessions.
- Docker Compose publishes backend on host port 8080 (8000 was already occupied on this machine), feed on 7100, receiver on 9900; `BACKEND_PORT`, `FEED_PORT`, and `WEBHOOK_PORT` override host bindings. Backend container uses feed/receiver service names, mounts kit `services/` read-only, and stores SQLite in the `dependency_watch_data` named volume.
- FastAPI runs locally with `python -m uvicorn app.main:app --app-dir backend --reload`; database tables and kit services are initialized on application startup.
